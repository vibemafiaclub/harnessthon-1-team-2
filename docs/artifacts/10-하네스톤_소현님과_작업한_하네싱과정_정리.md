# 1부. 소현님이 준 것 3가지

## 1-1. PRD 작성 프로세스 (Notion 문서)

소현님이 실제로 쓰는 PRD 템플릿. **5부 구성**이고, 이게 우리 하네스의 뼈대가 됐다.

| 부 | 소현님 문서에 있던 항목 |
|---|---|
| **1. 배경 및 목적** | 배경 / 목적 / **타깃 사용자(퍼소나 표: 유형·연령대·직업·사용목적)** |
| **2. 솔루션 및 기능** | 핵심 솔루션 **한 문장** / **Feature List 표 + 우선순위(High·Medium·Low)** |
| **3. 서비스 구조** | **정보구조(IA)** — 메인 메뉴 + 각 메뉴 설명 / **User Flow** (문장 + mermaid flowchart) |
| **4. 디자인 전략** | **레퍼런스 분석 — "무엇을 왜 차용하는지"** / GUI 톤&매너 + **왜 그 톤인지** |
| **5. 구현 전 기술 스펙** | 기능별 DB 설계 + 필요 API |

원 문서의 실제 사례는 **동대문 원단시장 앱**이었다(디자이너↔상인 소통, 오프라인 방문 유도).
거기서도 **당근의 매너온도를 벤치마킹**하고 있었고, 첨부로 `userflow.txt`·`flowchart.txt`(mermaid)가 함께 있었다.

> **우리가 배운 것**: PRD는 "무엇을 만들지"가 아니라 **"왜·누구를 위해·어디에 붙는지"** 를 먼저 쓴다.
> 특히 **4부의 "무엇을 왜 차용하는지"** — 레퍼런스를 나열하는 게 아니라 **차용 이유를 쓴다**는 점이 결정적이었다.

## 1-2. 레퍼런스 샘플 (실제 앱 캡처)

| 무엇 | 장수 | 우리가 뽑아낸 것 |
|---|---|---|
| **당근 실제 앱** | 5 | 나의 당근(회색배경+흰카드·서비스 그리드·매너온도) · **부동산 실거래가**(지역필터·큰숫자·직전최고가대비·스파크라인) · **단지상세**(언더라인탭·주황차트·필터칩) · **스플래시**(심볼+2줄카피+3D클레이) |
| **NOL 여행앱** | 10 | 검색카드(지역·날짜·인원) · 5×2 카테고리 그리드 · 지도 마커 · 목록 FAB · 테마 원형 캐러셀 |
| **토스 쇼핑** | 10 | 전폭 검색필드 · **연회색 pill 상단탭** · 연블루 배너카드(`2\|9` 인디케이터) · 포인트 섹션+파란뱃지 · **상품상세**(라벨/값 정보행·리뷰탭·하단 2버튼) |
| 토스 로고 | 1 | 브랜드 마크 |

## 1-3. 실시간 피드백 (이게 가장 값졌다)

만드는 족족 짚어준 지적들. **10건 전부가 초안 하네스에 없던 항목**이었다.

# 2부. ⭐ 소현님의 디자이너 인사이트 — 앞으로의 축

오늘 나온 지적을 **원칙으로 승격**한 것들. 앞으로 모든 디자인 작업의 기준이 된다.

## 축 1. "그 브랜드다움"은 색이 아니라 **정보구조와 어휘**에 있다

> *"당근스러운 느낌이 없다"*

색·폰트만 가져오면 **색만 같은 남의 앱**이 나온다. 실제로 첫 결과물이 정확히 그랬다.
브랜드다움은 아래 4개에 들어 있다.

| 요소 | 당근 사례 | 토스 사례 |
|---|---|---|
| **글로벌 내비** | 홈·동네생활·내 근처·채팅·나의 당근 | 홈·혜택·토스페이·주식·전체 |
| **기존 어휘** | 관심**목록**(관심종목❌) · 끌올 · 매너온도 | 전체 · 포인트 · 토스페이 |
| **공통 정보축** | 모든 항목에 **동(洞)** 이 붙는다 | 모든 항목에 **금액·적립**이 붙는다 |
| **인접 기능** | 당근페이 · 가계부 · 판매내역 | 저금통 · 토스페이 · 소비 · 혜택 |

→ **신규 기능은 N+1번째 탭이 아니다.** 기존 메뉴 트리 어딘가에 붙는다.
   (당근증권 = `나의 당근 → 당근페이 → 투자` / 토스여행 = `전체 → 여행`)

## 축 2. 레퍼런스는 **복제가 아니라 구성에 대한 피드백**

> *"레퍼런스의 구성을 피드백하라는 거지, 그대로 똑같이 만들라는 게 아니었어"*

| | 복제 | 비판적 차용 |
|---|---|---|
| NOL 홈에 카테고리 10개 | 우리도 10개 | *"10개 그리드는 백화점식 진열이다. 토스는 홈에 계좌 5개, 혜택에 미션 5개만 두는 **선택을 좁혀주는 앱**"* → **4개 + 전체보기** |
| NOL 최상단 = 특가 배너 | 우리도 특가 배너 | *"우리 존재 이유는 돈의 흐름"* → **여행 저금통** |

⇒ 스펙 단계에 넣을 질문: **"이 구성은 우리 제품의 어떤 원칙과 충돌하는가?"**

## 축 3. 메인 컬러는 **'포인트'** 다

> *"주황이 너무 남발되어서 어디에 집중해야 할지 모르겠다"*

**규칙**: 주색(진한 브랜드컬러) 면은 **화면당 "지금 눌러야 할 것" 1개 + 활성 탭**에만.
연한 컨테이너 색(`accentSoft`)은 면적이 커도 된다.

실제로 요약카드 배경·썸네일 배경·선택칩 배경에서 주황을 걷어내니 화면이 정리됐다.

## 축 4. 디자인 시스템은 **즉각즉각** 적용한다

> *"나중에 한꺼번에 적용하지 말자"*

나중에 몰아서 고치면 이미 만든 화면이 전부 어긋나 있어 **재작업 비용이 배로** 든다.
→ 화면 1개를 만들 때마다 그 자리에서 좌우 마진·섹션 여백·radius·타입 스케일을 적용한다.

## 축 5. 앱마다 **UX 라이팅 톤**이 있다 — 그대로 차용한다

| 앱 | 실제 문법 | 우리가 쓴 카피 |
|---|---|---|
| **당근** | *"첫 포인트, 오늘 받아볼까요?"* · *"지금 바로 구경해보세요!"* · 해요체·이웃 호칭·여유 | *"당근에서 번 돈, 그냥 두고 계셨죠?"* · *"오늘 번 돈으로, 오늘 시작해볼까요?"* |
| **토스** | *"얼마 받을 지 보기"* · *"누르면 바로 10원 받아요"* · 행동+결과, 즉시 이득, 담백 | *"지금 예약하면 18,400원 아껴요"* |

**공통 규칙**: 숫자에는 **비교 기준**을 붙인다(*"직전 최고가 대비 +2.3%"*, *"최근 3개월 평균(거래 2건)"*).
과장·명령형 금지(*"❗최대 76%"* ❌ → *"49,000원 · 조식 포함"* ✅).

## 축 6. 완성도의 실체는 **정렬·여백·줄바꿈**이다

> *"글자가 가운데정렬이 안 되고 상단에 붙어있다"* · *"마진값 특히 위아래가 일정하지 않다"* · *"줄바꿈이 불편하다"*

거창한 것이 아니라 이것들이 "투박함"의 정체였다. 실제 원인은:
- 텍스트 `verticalAlign` 기본값이 **top** (가운데 아님)
- 텍스트 폭이 컨테이너보다 좁아 **단어 중간에서 줄바꿈**("너 무", "옮 겨올")
- 섹션마다 상하 패딩이 제각각

## 축 7. 아이콘·로고는 **실물**을 쓴다

> *"기존 이모티콘 그대로 크롤링해서 넣어줘"*

임시 도형(회색 사각형)이 남아 있으면 완성도가 즉사한다.
- 당근 서비스 아이콘 8종 → **실제 앱 캡처에서 크롭**
- 토스 이모지 아이콘 8종 → **자산 페이지에서 크롭 + 다크배경 투명화**
- 기업 로고 → 파비콘 API로 조달
- 지도 → **레퍼런스의 실제 네이버맵 영역 크롭**

## 축 8. **상·하단까지** 시스템이 적용돼야 한다

> *"상하단 쪽 적용이 잘 안 되는 것 같다"*

본문만 정리하고 top bar·bottom nav를 방치하면 화면마다 높이가 다르다.
→ **Top app bar 64 / 좌우 16 / Navigation bar 80 / 콘텐츠 하단 여백 24** 를 전 화면에 고정.

## 축 9 (수민님). 하네스는 **무너지는 걸 본 뒤 그 영역만** 덧댄다

초안이 못 하는 게 확인된 지점에만, 그 시점에 단계를 만든다. **미리 다 만들면 대개 빗나간다.**

## 축 10 (수민님). 모델은 **일의 성격에 맞춰** 고른다

판단이 필요한 곳만 최상위 모델, 규칙이 정해진 검수는 Sonnet, 기계적 반복은 Haiku.
기준은 **"틀렸을 때 되돌리기 비싼가"**.

## 축 11 (수민님). 가장 중요한 것 — **디자이너가 어떤 프로세스로 일하는가**

도구가 아니라 **일하는 순서**가 하네스다. 그 순서가 단계로 들어와 있지 않으면 결과물은 초안에서 멈춘다.

# 3부. 디자인 시스템 — 원티드 제안 → Material 3

## 3-0. M3 이전에 먼저 나온 제안 — **원티드 디자인 시스템** (박소정)

디자인 시스템을 도입하기로 한 시점에 **가장 먼저 나온 후보는 M3가 아니라 원티드 디자인 시스템**이었다.

| 항목 | 내용 |
|---|---|
| 제안자 | **박소정** |
| 대상 | **Wanted Design System (Figma Community)** — [링크](https://www.figma.com/design/q61u3j2FDBqJOko20cQYiY/Wanted-Design-System--Community-) |
| 제안 이유 | *"이게 아주 좋다"* — 실무에서 쓰이는 **한국 서비스 기반** 디자인 시스템 |
| 진행 | 당시엔 파일 로딩 중에 M3로 방향이 바뀌어 내용을 못 봤고, **사후에 다시 열어 구조를 확인함**(아래) |

### 사후 확인 — 원티드 DS는 이렇게 생겼다 (2026-08-02 직접 열람)

| 항목 | 확인된 내용 |
|---|---|
| 공개 범위 | Figma Community 공개 파일 · **보기/댓글만 가능**(편집 불가) |
| 페이지 구성 | `Overview` · `Updates` · **`1 Theme`** · **`2 Element`** · **`3 Component`** |
| **3계층 구조** | **Theme(아이콘·로고) → Element(요소) → Component(컴포넌트)** 로 층이 나뉘어 있다 |
| 폰트 | **Pretendard** (썸네일에 명시) |
| 아이콘 | `1 Theme > 1 Icon` 보드에 **수백 개 규모의 아이콘 그리드** |
| 테마 | 썸네일에 **라이트·다크 양쪽** 화면이 함께 제시됨 |

> 정직하게: Overview 보드는 텍스트 스펙 문서 형태인데 **본문까지 정독하지는 않았다.**
> 위 표는 페이지 구조·폰트·아이콘 규모 등 **눈으로 확인한 사실만** 적은 것이다.

**흥미로운 일치**: 원티드 DS가 쓰는 **Pretendard**는, 우리가 당근 프로젝트에서 한글 본문 폰트로 고른 것과 같다.
한국 서비스용 디자인 시스템이 같은 선택을 하고 있다는 뜻이고, 이 판단이 틀리지 않았다는 방증이다.

### 그럼에도 이 제안이 남긴 것

이 제안이 **"디자인 시스템을 빌려오자"는 발상 자체를 열었다.** 그 전까지 우리는 토큰(색·폰트)만 뽑아 쓰고
**스페이싱·타입 스케일·컴포넌트 규격은 매번 즉흥적으로 정하고 있었다** — 그게 정렬·여백 지적의 원인이었다.
즉 **"기성 시스템을 통째로 차용한다"는 방향 자체가 소정님 제안에서 나왔고**, 최종 선택만 M3가 된 것이다.

### 왜 최종적으로 M3였나

| 기준 | 판단 |
|---|---|
| **문서화 수준** | M3는 **수치가 전부 공개 규격**(타입 15단·shape 6단·4dp 그리드·컴포넌트 높이)이라 지침에 그대로 박을 수 있다 |
| **하네스 적합성** | 우리 하네스는 **AI가 읽고 적용**해야 한다. Figma 파일은 사람이 보는 형태라 값 추출에 추가 단계가 필요 |
| **범용성** | 하네스는 "모바일앱 라이트모드 범용"이 목표. 특정 회사 시스템보다 **플랫폼 표준**이 이식성이 높다 |

> **다음에 다시 볼 가치**: 원티드 DS는 **한국어 타이포·한국 서비스 관습**(예: 한글 줄바꿈·조사 처리·리스트 밀도)이
> M3보다 잘 정리돼 있을 가능성이 높다. M3의 약점이 정확히 그 지점(라틴 기준 타입 스케일)이므로,
> **M3(뼈대) + 원티드(한글 타이포 보정)** 조합을 다음 라운드에서 검토할 만하다.

## 3-1. Material 3 — 왜 넣었고 무엇이 바뀌었나

## 왜 필요했나
축 6(정렬·여백)의 지적이 반복됐다. 매번 눈으로 고치는 대신 **수치가 규정된 시스템**이 필요했다.
M3는 타입 스케일·shape·4dp 그리드·컴포넌트 규격이 전부 정해져 있어 **"일정하지 않다"는 문제가 구조적으로 사라진다.**

## 우리가 정한 원칙: **뼈대는 M3, 색과 말투는 브랜드**

| M3가 주는 것 | 브랜드가 주는 것 |
|---|---|
| 타입 스케일 · shape 스케일 · 4dp 그리드 · 컴포넌트 규격 · 접근성 | 색 role 값 · 폰트 · 어휘 · UX 라이팅 톤 |

## 실제 적용값

| 항목 | 값 |
|---|---|
| **색 role** | primary / primary-container / surface / surface-container / on-surface / on-surface-variant / outline-variant + custom(up·down) — **브랜드 색을 M3 role에 매핑** |
| **타입 스케일** | displayS 36 · headlineM 28 · headlineS 24 · titleL 22 · titleM 16 · titleS 14 · bodyL 16 · bodyM 14 · labelL 14 · labelM 12 |

## 5-2. 레퍼런스 삼각측량 (오늘 가장 효과 컸던 방법)

한 곳만 보면 복제가 되고, **세 곳을 보면 판단이 생긴다.**

| 축 | 얻는 것 | 당근증권 | 토스여행 |
|---|---|---|---|
| 1. 과제 자산 | 색·폰트·IA·어휘 (SSOT) | `1-daangn` | `3-toss` |
| **2. 같은 회사의 인접 서비스** | **그 회사가 이 도메인을 어떻게 푸는가** | 당근 **부동산** | 토스 **쇼핑** |
| 3. 도메인 1위 앱 | 관습(레이아웃만) | 토스증권 | NOL 여행 |

**축 2가 결정적이었다.** 당근 부동산이 이미 *"큰 숫자 + 직전 최고가 대비 + 지역 필터"* 를 풀어놨고
그게 증권 화면의 답이었다. **인접 서비스를 안 보면 반드시 남의 앱이 된다.**

## 5-3. 안전장치

- **작업 Page 게이트 2단** — 전환 전용 호출 + 저작 후 **생성 노드 소속 검증**(실시간 공유 파일 사고 방지)
- **읽기 전용 계약** — 자산 Page는 `openPage` 금지, 참조로만 순회
- **재실행 안전** — deterministic 네이밍 + skip/update (중복 누적 방지)
- **반하드코딩** — 자산 Page명·색·규격·폰트 전부 인자/추출값. 지침에 고유명사 0

## 5-4. 실측 함정 22종 (모르면 시간을 통째로 날리는 것들)

대표적인 것만:
- `page.children`은 **없다** → `page.root.children` (틀리면 **에러 없이 빈 배열** = 조용한 실패)
- `fills`는 배열이 아닌 **프록시** → `.map/.forEach` 던짐
- `findByName("Inter")` → **`Inter Tight`** 반환(부분일치) → `fonts.all.find(정확일치)`
- 인스턴스는 **구조 변경이 전파되지 않는다** → 새 이름으로 새 컴포넌트
- 텍스트 `verticalAlign` 기본 **top**
- **대용량 PNG 병렬 임포트 → 플러그인 정지** (780px 이하 + 2~3장씩)
- **플러그인 탭 2개 = 전 호출 실패**
- 타임아웃이어도 **실제로는 반영된 경우가 많다** → 재실행 전 되읽기
